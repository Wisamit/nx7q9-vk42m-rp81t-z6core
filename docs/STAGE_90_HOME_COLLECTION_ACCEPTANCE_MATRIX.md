# Stage 90 — End-to-End Home Collection: Booked Order → Specimen Barcodes → Branch Handoff → Invoice

## Project baseline and actual gap
The owner confirmed successful Stage 89 deployment, requested **larger feature-complete stages**. Reviewed `02_MASTER_SCOPE.md` §§20–24,33,45,63,79,80,85 and the existing `/digital-services` APIs/console. Scheduling, basic home visit statuses, queue and laboratory order/payment/specimen pipelines already existed. Previously a home visit could reach `COLLECTED`/`DELIVERED` by changing a status **without evidence of an actual linked clinical order, collected barcoded specimens or laboratory receipt**. The existing visit had no FK to the LIS accession; specimen attempts had no FK to the appointment visit.

## End-to-end operator workflow now
1. Reception registers the patient, creates the actual priced LIS laboratory order using the existing catalog/pricing/specimen engine, and confirms a HOME_COLLECTION booking. In `/home-collections/[id]`, an authorized `home_collection.manage` AND `orders.view` user links **one existing accession** matching the exact organization, active branch and patient; an order cannot be bound to two home visits, and linking only occurs before dispatch. The new linkage is a nullable/unique FK to the original `LabOrder`, with actor/time and audit, **not a fabricated clinical order**.
2. `/home-collections` is a branch-filterable 100-item-paged operational dispatch board. Staff with `specimens.collect` only see their assigned home visits; managers see branch visits; receiving staff can see delivered/handoff candidates. Each case page shows time/address, patient, assigned collector, source order/tests, actual invoices with separate original-currency totals/paid/balance, and per-specimen barcode/proof status.
3. Manager assigns an authorized branch collector. Assigned collector can update EN_ROUTE → ARRIVED → COLLECTING → COLLECTED; only management can finalize branch DELIVERED. The server reauthorizes user, branch and collector and validates transitions under row locks.
4. Starting COLLECTING requires a linked accession, assigned collector, expected specimens and at least one **issued** non-void LIS invoice. **Unpaid credit invoices remain outstanding**, are shown in the original currency and are never auto-marked paid or converted.
5. Actual HOME collection occurs exclusively through the existing two-identifier `/phlebotomy` barcode workflow. It sends the visit ID and records it on immutable `SpecimenCollectionAttempt` together with patient identity verification, branch, actor, location and volume. Both successful and failed/recollection attempts retain the lineage. The transaction locks the appointment and home visit **before** the specimen, rejecting canceled, unassigned or concurrently changed visits.
6. Switching COLLECTING → COLLECTED requires a SUCCESS collection attempt linked to this visit and assigned collector for **every required physical specimen** (recollection handled via exclusion of failed originals, aliquots don't count as separate original tubes). Changing status alone cannot synthesize evidence. For COLLECTED → DELIVERED, every physical specimen must independently be `RECEIVED` or `IN_PROCESS` with a formal `SpecimenReceptionAssessment` at the correct branch. Quarantined/rejected/unlabeled samples cannot be silently considered accepted. An atomic transaction then marks the visit DELIVERED and booking COMPLETED, recording audit/custody attestation.
7. Each new API uses tenant-scoped and branch-scoped checks, optimistic state claims and Serializable order/visit locks. Existing historic appointments and specimen attempts are preserved with nullable new fields; they are **not backfilled with invented chain-of-custody evidence**.
