# Stage 87 — Immutable Clinical Comment Template Revisions

## Verified need / source of truth
Stage 86 merged on `main` `111298853e1e8e248027e8479b5fdc3183a11118`, main CI #1085 SUCCESS, and owner confirms Hostinger deployment. Master Scope §37 needs configurable comment templates at component/test/order/report; §40 forbids destructive released-result edits; §§41,80 require audit and historical snapshots. The current result-comment templates could be approved/retired but lacked any safe mechanism to **revise approved wording** without overwriting approved source text or losing its previous identity.

## Implemented operator workflow
1. `/clinical-comments/revisions` is accessible to `result_comments.manage` users with an ACTIVE branch grant in their organization. It shows current approved English/Arabic text **read-only**, test/component scope and code; operator documents a reason (10–1000 chars) and changes text/names using bilingual fields. A capped and cursor-paginated list avoids hiding templates past the first page.
2. `POST /api/clinical-rules/comments/revisions` validates exact source fingerprint and nontrivial clinical change, then locks the ACTIVE organization, ACTIVE granted branch, parent template and ACTIVE tenant-owned clinical targets. It creates an **INACTIVE** child with immutable parent pointer `supersedesTemplateId`, revision number, new unique code and audit `RESULT_COMMENT_TEMPLATE_REVISION_CREATED` in a Serializable transaction. No text in the predecessor is rewritten.
3. Additive Prisma migration introduces `revision_number` default 1, nullable FK `supersedes_template_id` and a **unique** successor constraint preventing forks. Old templates keep their status and clinical text, revision 1, no predecessor. The schema references the same organization-level template model, not per-test tables.
4. The existing independent approver queue now includes revised drafts and creator audit provenance, current predecessor and lineage. Approval uses Stage 85/86 exact full-text fingerprint now also bound to predecessor and revision number; requires distinct reviewer, `clinical_rules.approve`, `result_comments.manage`, active branch, clinical reason and explicit `APPROVE_REVISION_AND_RETIRE_PREDECESSOR` attestation.
5. Upon approval, in one locked Serializable transaction the child becomes ACTIVE and its **still-ACTIVE exact predecessor becomes INACTIVE**; two audit events record predecessor retirement and child approval with reviewer/reason/IP/branch/full fingerprints. If predecessor has become inactive/invalid or row is stale, the **entire transaction rolls back**. A parent with any successor cannot later be reactivated. Existing Stage 85 non-revision approval behavior remains unchanged.
6. No released result, result comment snapshot, report version, patient record, invoice, reference range or price is rewritten. No automatic clinical meaning inference. Approval changes only which reusable text may be selected for future work; existing reports retain their issued content.
