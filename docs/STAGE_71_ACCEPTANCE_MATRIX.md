# Stage 71 — Exact Result Revision / Report Snapshot Integrity in Longitudinal Patient History

## Clinical safety issue
The longitudinal patient history already used only the **current, non-retracted diagnostic report version** and branch/department scoped results. However it extracted only `resultId` from each current report's `resultVersionSnapshot`. When resolving that ID, the code did not require the stored report pointer's `orderItemId` and `resultVersion` to match the actual clinical result, nor did it establish that the referenced result belongs to the diagnostic report's own `orderId`. Corrupt or misplaced report pointers could lead to displaying an unrelated result revision or incorrect longitudinal trend.

## Stage 71 implementation
- `src/lib/patient-history.ts`: new `currentReportResultPointers` reads only the current report revision in states `PARTIAL`, `FINAL`, or `AMENDED`, validates each pointer's nonempty result/item IDs and positive safe integer revision, and captures the current report's immutable `orderId`. Conflicting mentions of one `resultId` with different `orderId`, `orderItemId` or `resultVersion` are excluded **from all current evidence** (fail closed). `resultMatchesCurrentReportPointer` verifies all three dimensions against the resolved result. The legacy pure helper is retained for existing exported API compatibility but is no longer used in the clinical history view.
- `src/app/patients/[id]/history/page.tsx`: select report `orderId` together with `currentVersion` and snapshot. Query only report-referenced result IDs (as before), then **filter against exact immutable pointer tuples** before selecting latest clinical result versions and composing cumulative tables and numeric trends. Do not expose or trend conflicting, incomplete, stale, withdrawn or wrong-order revisions.
- `tests/stage-71-patient-history-report-pointer-integrity.test.ts`: valid pointer vs wrong order/item/revision, withdrawn and stale versions, malformed values, duplicate/conflicting references, result trend version preservation and server permission/visibility invariants. Update longitudinal history regression assertion.
- `tests/stage-71-patient-history-report-pointer-mariadb.integration.test.ts`: real MariaDB patient, two orders, order items and immutable laboratory result revisions. A report's old version references an old result; current amended report version includes correct amended result and an incorrect pointer to another order. Current second report also references that result; conflicts are suppressed. Test checks original rows stay unchanged, no other-tenant leakage and latest authorized trend revision only.
- CI retains all existing gates, including schema/migrations, patient merge, billing and report immutability, and adds a dedicated Stage 71 MariaDB test.

## Unchanged access and history rules
The patient remains organization-wide and merged aliases are resolved without altering original identity/history. Access is still intersected with the permitted report/order/result performing branches and allowed departments, `reports.view` is required to show results, and `patients.view` is required for history. The result and report must remain `RELEASED`/`AMENDED` and current `PARTIAL`/`FINAL`/`AMENDED`, respectively; retracted reports remain excluded. Trend grouping continues to separate method, analyzer and units, and the results page explicitly labels its 20-record limit rather than calling it a complete longitudinal trend.

## Constraints
- **Read-only display safety change.** No report/result amendment, clinical release, sign-off, catalog price change, audit deletion, patient rewrite, database schema migration or environment variable change.
- Conflicting pointers are intentionally hidden pending data-integrity investigation. No attempt to guess, reinterpret or repair historical clinical records.
- Only CI-verified exact merged SHA is eligible for Hostinger deployment. Manual UAT and final clinical signoff remain deferred as previously agreed. Draft Analyzer Bridge PR #128 is not included.
