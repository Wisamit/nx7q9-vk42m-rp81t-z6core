## Functional coverage
1. **Independent patient entitlement:** `doctor_portal_patient_access.can_request_orders`, additive and **FALSE by default** for all existing grants. Admin can grant the privilege explicitly on a new patient-specific grant with effective dates and full audit, independently of viewing orders/reports; staff can revoke with an audited reason. No implicit migration of existing view grants to ordering.
2. **Physician portal:** Authorized DOCTOR with active session and referrer, valid patient-specific ordering grant and active tenant/branch/test context may submit up to 25 unique, active tests. Request contains patient, receiving branch, urgency, original indication/notes and catalog identity/display-name snapshots. Bilingual UI shows eligible patients only; patient name is never the identity used for processing.
3. **Separate request queue:** `DoctorRequisition` and `DoctorRequisitionItem` are normalized and have UUID/FK, immutable request key, fingerprint, ordering context and status (`SUBMITTED`, `CANCELLED`, `DECLINED`, `FULFILLED`). No core `LabOrder`, specimen, result, invoice or price is generated by physician submission. Exact replay of the same key/payload is idempotent; conflicting payloads are rejected.
4. **Auditable transitions:** Physician can cancel only an unprocessed own request, reception staff with `orders.create` can decline with a detailed reason, and all state changes have transaction/CAS and an audit trail. Race between cancel, decline and conversion cannot create conflicting outcomes.
5. **Reception registration:** Branch-scoped `/doctor-requisitions` review worklist with status/history, pagination and link to prefilled order registration. Patient, doctor, branch, selected tests, priority and original clinical text remain unchanged. Reception independently selects the proper billing source/client and handles required question answers, existing financial/discount/tax/credit policies, specimen planning, and generated accession/invoice via the **existing** `POST /api/orders` workflow.
6. **Atomic conversion:** Existing order creation optionally accepts `doctorRequisitionId`; transaction locks request row before financial mutations, checks same tenant, allowed receiving branch, exact patient/referrer/test IDs, priority and clinical text, then atomically links to newly created lab order with `FULFILLED` and audit. Concurrent staff operators cannot register the same referral twice, and failure rolls back entire order/invoice/requisition transaction.
7. **Cross-branch governance:** Organization-wide patient record unchanged. Requested branch must belong to same tenant; staff worklists and transition checks enforce their active branch scope. The request does not assume any analyzer/test is available until existing reception routing validation runs.
